# Bakieva Chat | Вступить в чат

Telegram-бот на Node.js 22+, TypeScript, grammY и PostgreSQL. Продаёт доступ к закрытому каналу и чату через существующую ссылку Kaspi Pay. Проверка реального поступления остаётся ручной: новый API-ключ Kaspi не требуется.

## Покупка и доступ

1. Клиент принимает документы, выбирает «1 месяц» (по умолчанию 5 000 ₸ / 30 дней) или «6 месяцев» (25 000 ₸ / 180 дней).
2. Бот сохраняет отдельную покупку со снимком тарифа, суммы, срока и имени. Изменение тарифа не меняет старые покупки. До заявления об оплате заявку можно отменить кнопкой; после — её проверяет администратор.
3. Клиент оплачивает по ссылке Kaspi и нажимает «Я оплатил(а)». Это только заявка, не продажа. Администратор сверяет сумму и фактическое поступление в Kaspi Pay, затем подтверждает или отклоняет заявку.
4. Подтверждённая оплата сохраняется, даже если клиент не предоставил WhatsApp. Без номера и отдельного согласия на обработку данных подписка этой покупки не активируется и приглашения не отправляются. Срок начинается после выполнения этих условий; действующая подписка продлевается от более позднего из текущего окончания и настоящего момента.
5. Клиент вводит WhatsApp вручную или делится собственным Telegram-контактом, затем подтверждает нормализованный номер. Чужие и неопределённые contact.user_id не принимаются. Проверяется структура номера, но не регистрация или владение аккаунтом WhatsApp. Ручной ввод требует заявления «Это мой номер»; OTP-проверки нет.
6. Приглашения работают через Telegram join requests. Бот проверяет одновременно Telegram ID, чат, сохранённую ссылку, её срок, подтверждённую оплату, активную подписку, WhatsApp и согласие. Пересылка ссылки другому аккаунту не даёт права вступления.

Повторное подтверждение оплаты и повтор Telegram update не добавляют срок второй раз. Изменения оплаты, активации, продления, вступления и отзыва сериализуются блокировкой пользователя в PostgreSQL. Уже сохранённый WhatsApp повторно не запрашивается. Ошибки Telegram не отменяют подтверждённую покупку.

Команды клиента: /start, /menu, /access (продолжить оформление или обновить приглашения), /whatsapp (исправить номер), /subscribe, /unsubscribe, /delete_data. Приглашения действуют час. Продлённая подписка не требует повторного вступления, если пользователь остался участником.

## Настройка и запуск

Обязательны BOT_TOKEN, DATABASE_URL, ADMIN_IDS. Для платного сообщества настройте PAID_CHANNEL_ID и PAID_CHAT_ID, а также документы OFFER_URL, PRIVACY_URL, DATA_CONSENT_URL, SUBSCRIPTION_TERMS_URL. Если документы не настроены, новая покупка не начинается. FREE_CHANNEL_URL и TRIAL_LESSON_URL необязательны; пустые значения допустимы.

Старые переменные SUBSCRIPTION_PRICE=5000 и SUBSCRIPTION_DAYS=30 задают начальные условия месячного тарифа. Добавлены необязательные HALF_YEAR_PRICE=25000, HALF_YEAR_DAYS=180 и SALES_REPORT_TIME=09:00. Новых обязательных переменных нет. После первого создания тарифов значения хранятся в PostgreSQL: меняйте их кнопками /admin либо /plan. Старое сохранённое settings.price переносится в месячный тариф; проверьте цены перед выпуском.

KASPI_PAY_URL и SUPPORT_PHONE сохраняют существующие значения по умолчанию. NEWS_TARGET_CHAT_IDS, TELEGRAM_API_ID и TELEGRAM_API_HASH продолжают работать. Секреты задаются в Railway, не коммитятся в Git.

~~~sh
npm install
npm run typecheck
npm run build
npm test
npm start
~~~

Для воспроизводимой установки используйте npm ci и сохранённый package-lock.json. /healthz проверяет процесс, /readyz — готовность polling и PostgreSQL. При запуске до polling применяются миграции и создаются отсутствующие тарифы. Планировщик работает раз в минуту, запускается после готовности бота и останавливается при SIGTERM. Используйте один polling-экземпляр на токен; несколько одновременно работающих ботов конфликтуют в Telegram getUpdates, даже при корректных блокировках БД.

Для локальных SQL-тестов npm test использует изолированную PGlite без production-credentials. Для всех тестов, включая конкурентные транзакции, задайте TEST_DATABASE_URL на отдельную локальную PostgreSQL-базу с именем bakieva_test (или bakieva_test_SUFFIX). Тесты очищают эту тестовую БД. Другие адреса и имена отклоняются. GitHub Actions поднимает PostgreSQL 16 и выполняет typecheck, build и полный набор тестов. Telegram API в тестах подменён транспортом; реальные Kaspi/Telegram операции в production тесты не выполняют.

## Администрирование и отчёты

Все команды с персональными данными и административные действия доступны только ADMIN_IDS в личном диалоге с ботом. /admin содержит кнопки продаж, реестра, контактов, активных подписок, ожидающих оплат, отсутствующего WhatsApp, тарифов, отчётов, продления и отключения. Реестр показывает историю покупок постранично; один покупатель может иметь несколько покупок. Неоплаченные заявки не входят в выручку.

~~~text
/sales_today
/sales_yesterday
/sales_report YYYY-MM-DD YYYY-MM-DD
/sales_export
/contacts_export
/contacts_marketing
/plan month 5000 30
/plan half_year 25000 180
/price 5000
/report_time 09:00
/grant TELEGRAM_ID DAYS
/extend TELEGRAM_ID DAYS
/revoke TELEGRAM_ID
/payment_plan PAYMENT_ID month|half_year
/admin_cancel
~~~

/price меняет только месячный тариф. /plan меняет цену и необязательно длительность независимо для каждого тарифа. Существующие снимки покупок сохраняются. /grant и /extend — учтённые административные продления уже оплаченного покупателя с завершённым профилем; они не создают продаж и не обходят обязательные условия доступа. Повтор того же update не продлевает срок повторно. /revoke отключает доступ; неудачное удаление из Telegram повторяется планировщиком.

Ежедневный отчёт отправляется всем администраторам за предыдущий календарный день после настроенного времени (Asia/Almaty). Он содержит полный список подтверждённых покупок, имена, Telegram ID, WhatsApp, тарифы, суммы, сроки и статусы, количество покупок и покупателей, разбивку по тарифам, выручку, текущие очереди проверки и отсутствующего WhatsApp. Длинный текст разбивается; дополнительно отправляется CSV. /sales_report без аргументов предлагает ввести период. Границы дат включительны и рассчитываются PostgreSQL по Asia/Almaty, без фиксированного UTC-смещения.

Каждая дата и получатель имеют запись доставки, каждая часть — свой статус и Telegram message_id. При штатном перезапуске отправленные части не повторяются; известная ошибка Telegram повторяет только неотправленную часть. Telegram не предоставляет ключ идемпотентности: таймаут или падение после отправки до записи результата создают неопределённость. В этом случае автоматический повтор прекращается:

~~~text
/sales_delivery
/sales_resolve DELIVERY_ID PART sent
/sales_resolve DELIVERY_ID PART retry
~~~

Сначала сверьте диалог получателя. sent отмечает уже полученную часть; retry явно разрешает повтор, при ошибочной сверке возможен дубликат. Части нумеруются с нуля. Снимок отчёта сохраняется для возобновления. /sales_export выгружает все подтверждённые покупки, включая обезличенные; заявки видны отдельно в админ-панели.

CSV использует UTF-8 BOM, CRLF и экранирование кавычек. Текстовые формулы обезвреживаются. В контактах phone_e164 содержит точный международный номер для импорта; phone_excel_text — безопасное текстовое представление для открытия в Excel. При импорте phone_e164 в Excel выберите тип столбца «Текст». Маркетинговый экспорт включает только текущее явное согласие с датой; отказ действует сразу. Прямой массовой WhatsApp-рассылки нет.

Старые /set about, /set content, /set trial_url, /set free_channel_url и /broadcast сохранены. /broadcast отправляет только явно подписавшимся пользователям. /subscribe — добровольное включение; /unsubscribe отключает рассылку.

## Миграции и существующие данные

migrations/001_init.sql сохранена без изменений. Мигратор последовательно применяет все SQL-файлы под advisory lock, в транзакции, и хранит имя, checksum и дату в schema_migrations. Повторный запуск безопасен; изменение уже применённой миграции останавливает запуск вместо молчаливого изменения истории.

002_commerce.sql добавляет тарифы, снимки покупок, данные профиля, приглашения, административные действия и доставку отчётов. Старые пользователи, суммы, статусы, история оплат, новости и действующие сроки не сбрасываются. Архивные покупки помечаются legacy; неизвестный исторический срок не выдумывается. Они не активируются повторно. Для незавершённой архивной заявки администратор явно назначает тариф через /payment_plan, сохраняя исходную сумму, затем проверяет платёж.

Существующих участников миграция не удаляет. Для новых приглашений, включая восстановление доступа старого покупателя, нужен WhatsApp и согласие. Прежний автоматический marketing_opt_in=TRUE не доказывает добровольное согласие: записи без зафиксированной даты явного согласия выключаются. Для рассылок потребуется /subscribe.

/delete_data требует отдельного подтверждения клиентом, отзывает доступ и удаляет профиль, телефон, согласия и учёт участника. Покупки остаются с суммами и тарифами, но без Telegram ID, имени, телефона и привязки к профилю. Серверные снимки отчётов с этим ID обезличиваются. Уже доставленные Telegram-сообщения, скачанные экспорты и резервные копии требуют отдельной обработки владельцем; бот не обещает удаление из чужих устройств. Владелец определяет сроки хранения и порядок обработки таких запросов.

Перед выпуском изучите docs/PRODUCTION.md. Изменения production, применение миграций на production и деплой требуют отдельного разрешения владельца.

## Публикация новостей в группы и каналы

Администратор открывает личный чат с ботом → `/admin` → **📰 Опубликовать новость** (или `/news`). После этого отправляет **одно** сообщение с текстом, фото/видео и подписью либо документ/аудио. Бот копирует сообщение в каждый настроенный чат через Telegram Bot API и возвращает отдельный результат для каждого получателя. Отчёт доступен повторно через `/news_report`.

По умолчанию получатели — **PAID_CHANNEL_ID** и **PAID_CHAT_ID**. Дополнительные получатели задаются переменной Railway `NEWS_TARGET_CHAT_IDS=-1001234567890,-1009876543210` (ID через запятую). Дубликаты ID исключаются. Ссылки типа `FREE_CHANNEL_URL` недостаточно: для публикации нужен числовой Telegram chat ID и права бота. Telegram не предоставляет боту полный список всех групп, в которых он состоит, поэтому нужные группы должны быть указаны явно.

Бот должен быть участником каждой группы с правом отправлять сообщения, а в каналах — администратором с правом публикации. При ошибке (например, нет доступа или бот удалён) соответствующий адресат будет отмечен как неуспешный. Для каждой успешной отправки сохраняется возвращённый Telegram `message_id`; по возможности отчёт содержит прямую ссылку на публикацию (для приватных групп она доступна только участникам). Статусы хранятся в PostgreSQL (`news_publications`, `news_deliveries`), таблицы создаются при запуске.

Команды `/news`, `/news_cancel` и `/news_report` действуют только для ID из `ADMIN_IDS` и только в личном чате с ботом. Режим ожидания истекает через 10 минут. Альбомы из нескольких файлов не поддерживаются — отправляйте одним сообщением. Новость публикуется сразу после её отправки администратором, без дополнительного подтверждения. Перед первой реальной публикацией проверьте список адресатов.

 
## Учёт участников: кто вступил до бота и после него

Бот автоматически записывает вступления и выходы в **PAID_CHAT_ID**, **PAID_CHANNEL_ID** и все чаты из **NEWS_TARGET_CHAT_IDS** (одна запись на каждого человека в каждом чате). В этих чатах ему нужны права администратора, чтобы получать изменения статуса участников. В `src/index.ts` явно запрошен тип обновлений `chat_member`.

Команды доступны **только администраторам из ADMIN_IDS в личном диалоге с ботом**:

- `/members` — сколько людей зафиксировано в каждом чате и сколько числится в Telegram (если доступно); кнопки отчёта, синхронизации и экспорта;
- `/members_list` — последние 25 записей (вступление, Telegram ID, чат);
- `/members_export` — CSV-реестр всех **известных боту** участников, в том числе вышедших;
- `/members_sync` — сверить пользователей, уже известных боту, с текущим составом групп через Bot API; при настройке API_ID/HASH дополнительно попытаться собрать **существовавших до бота** участников через MTProto.

Каждое новое вступление отправляется личным уведомлением администраторам с ID, именем, названием чата и фактическим временем события (часовой пояс Алматы). В PostgreSQL хранятся `chat_memberships` и `membership_events`. Неизвестные даты вступления **не заменяются датой синхронизации**: поле `joined_at` остаётся пустым, а момент обнаружения содержится отдельно в `first_seen_at`. Если Telegram сообщает дату вступления в ответе MTProto для обычного участника, она сохраняется с источником `mtproto`. Для администраторов дата назначения на роль **не считается** датой вступления.

### Подключение исторической синхронизации

Помимо уже обязательных переменных Railway добавьте:

- `TELEGRAM_API_ID` — числовой App api_id с [my.telegram.org](https://my.telegram.org/apps);
- `TELEGRAM_API_HASH` — секретный App api_hash оттуда же.

Библиотека GramJS выполняет MTProto-вход **как тот же бот** через `BOT_TOKEN`; никаких логинов пользователей по телефону или сессионных ключей администраторов не требуется. Без MTProto-переменных команда `/members_sync` может проверить только Telegram ID, которые уже записаны в таблице пользователей бота (до 2000 за запуск). После настройки MTProto откройте личный чат с ботом и выполните `/members_sync` ещё раз. Сервис опросит супергруппы и каналы, ID которых начинается с `-100`, и сохранит найденный реестр. Обычные небольшие группы требуют отдельного способа импорта.

**Ключевое ограничение:** Telegram Bot API не предоставляет полный список старых участников, а MTProto может ограничить или скрыть результаты даже при наличии прав. Для приватных чатов может понадобиться разрешение Telegram на доступ к peer через MTProto (нулевой access hash поддерживается не во всех контекстах). Синхронизация может вернуть не всех: сравнивайте `/members` с количеством участников в Telegram. Нельзя восстановить даты вступления пользователей, чьи события не сохранились и которые уже покинули группу. Не обещайте полноту и не считайте `first_seen_at` фактическим временем вступления.

Содержимое реестра персональное; доступ к нему должен оставаться только у администраторов. Не включайте API_HASH в сообщения или git-коммиты.
