# Проверка кандидата к выпуску

## Карта архитектуры

## Найденные и исправленные дефекты

- Подписка выдавалась сразу при подтверждении оплаты, без WhatsApp. Подтверждение теперь сохраняется отдельно от активации; без обязательного профиля состояние `waiting_profile`.
- Цена и срок отсутствовали в истории покупки; будущие изменения могли менять смысл оплаты. Новая заявка получает неизменяемый снимок тарифа, суммы и срока.
- `member_limit=1` не связывает приглашение с покупателем. Новые приглашения используют `creates_join_request`, без несовместимого `member_limit`; проверяются сохранённый URL, чат, Telegram ID и все условия доступа. См. [Telegram Bot API](https://core.telegram.org/bots/api#createchatinvitelink).
- Проверка существующей pending-заявки и её создание могли гоняться. Покупки и изменения подписки выполняются под общей блокировкой пользователя. Сохранённый update ID защищает от повторного создания после обработки исходной заявки.
- Повторное административное продление могло увеличивать срок дважды. Действие записывается с уникальным Telegram update ID.
- Удаление участника подавляло исключения, после чего подписка помечалась истёкшей. Сейчас неудачное удаление остаётся в очереди; после блокировки повторно проверяется актуальность срока, чтобы не удалить уже продлившегося пользователя.
- Поздний WhatsApp после явного отзыва не должен активировать отозванную покупку. Активация разрешена только из `waiting_profile`.
- Запуск применял только `001_init.sql`. Новый мигратор применяет файлы по порядку в транзакции, ведёт журнал и проверяет checksum.
- Маркетинг был включён автоматически. Теперь требуется явная дата согласия; выгрузка аудитории и `/broadcast` учитывают текущее согласие.
- Старые административные команды могли отправлять персональные данные в групповой чат. Чувствительные взаимодействия ограничены личными чатами и `ADMIN_IDS`.
- Сырые исключения могли попасть в сообщения и логи. Неизвестные ошибки заменены безопасными описаниями; SQL-state и Telegram code сохраняют диагностическую пользу без параметров запросов и секретов.
- Повторные/устаревшие события участников могли испортить текущий статус. Изменения одной пары чат–пользователь сериализуются, более старые события не заменяют новое состояние.
- Старый Vitest тянул уязвимые зависимости тестового окружения. Обновление и lockfile устраняют выявленные npm audit зависимости. Тесты не входят в новую сборку runtime и не запускаются повторно из `dist`.

## Проверки

`npm install`, `npm run typecheck`, `npm run build`, `npm test` выполнены локально. Полный набор дополнительно запускается на отдельном PostgreSQL 16.14 с несколькими соединениями; тестовые данные находятся исключительно в локальной `bakieva_test`. GitHub Actions повторяет проверки на PostgreSQL 16 и Node.js 22. Окончательное число тестов и результат CI указаны в PR.

Набор покрывает оба тарифа; pending без доступа; права администратора; подтверждённую оплату без WhatsApp; оба согласия; корректные и ошибочные телефоны; чужой контакт; подтверждение и исправление номера; повторную оплату и update; восстановление незавершённого профиля; expiry/revoke и ошибки Telegram; чужой аккаунт/чат/ссылку; полный список покупателей, пустой день, часовую зону и CSV; маркетинговый фильтр; повтор/неопределённость отчёта; реальную SQL-миграцию старой схемы; обезличивание; старые новости и учёт участников; health/readiness. Сквозной тест передаёт updates через реальные обработчики grammY и пересоздаёт бота между вводом и подтверждением телефона.

Параллельные тесты на PostgreSQL проверяют единственную активацию при восьми подтверждениях, отсутствие дубликатов pending-заявки, сохранение продления, единственную доставку отчёта при нескольких воркерах и отказ во вступлении после отзыва.

Telegram API подменён в тестах: реальные права бота, доступность чатов, Kaspi и реальные доставки не подтверждены этими тестами. Структурная проверка телефона не доказывает регистрацию WhatsApp или владение SIM. Миграция проверена на старой SQL-схеме с синтетическими пользователями, а не на копии production-БД.

22 октября 2026 проверка действующей конфигурации Railway через подключённый коннектор не состоялась: после подтверждённой авторизации инструмент вернул `requires a non-empty string link_id argument`. Локальная Railway CLI отсутствует. Значения production-переменных, production-БД и настройки сервиса не читались и не изменялись; совместимость команд запуска и кода проверена локально. Текущие настройки Railway должен сверить владелец перед выпуском.

## До разрешённого выпуска

1. Владелец проверяет PR и отдельно разрешает деплой. До этого не применяйте миграцию к production и не запускайте вторую копию бота с действующим токеном.
2. Проверьте актуальную резервную копию PostgreSQL и восстановление в отдельной среде по принятой процедуре. После миграции не откатывайте на старую логику выдачи доступа; схема добавочная, а откат приложения может обходить новые обязательные проверки.
3. В Railway должны сохраняться `DATABASE_URL`, `BOT_TOKEN`, `ADMIN_IDS`, ID платных сообществ и ссылки на документы. Новых обязательных переменных нет. Необязательны `HALF_YEAR_PRICE=25000`, `HALF_YEAR_DAYS=180`, `SALES_REPORT_TIME=09:00`. После создания тарифов меняйте их в БД через `/admin`, не изменением исходного кода.
4. Сборка: `npm ci` → `npm run build`; запуск: `npm start`. Для проверки готовности используйте `/readyz`, для liveness `/healthz`. Только один активный polling-экземпляр на Telegram-токен; старый процесс должен остановиться перед запуском нового.
5. Бот должен быть администратором закрытого канала и супергруппы с правами приглашать/одобрять заявки и удалять участников. Другие администраторы и существующие ссылки могут отдельно открывать доступ: отзовите старые обычные ссылки и ограничьте ручное добавление. Bot API не позволяет перечислить и отозвать все приглашения других администраторов автоматически. Бот не добавляет пользователей принудительно.
6. До реальной продажи проверьте цены и длительности обоих тарифов в `/admin`; существующий `settings.price` сохраняется. Архивные ожидающие заявки видны администратору; назначьте им тариф через `/payment_plan` только после уточнения заказа.
7. В отдельном Telegram-тестовом сообществе пройдите оба тарифа, повторную оплату, отсутствие WhatsApp, неправильный контакт, пересылку приглашения, отзыв и истечение. Проверьте получение полного отчёта и CSV всеми администраторами. Реальное поступление Kaspi сверяет человек.
8. Уведомите прежних покупателей о WhatsApp для восстановления приглашений и о повторном добровольном `/subscribe`, если нужен маркетинг. Действующие участники и сроки автоматически не сбрасываются.
9. Определите хранение персональных выгрузок и обработку запросов на удаление. `/delete_data` обезличивает серверные покупки, но не стирает ранее скачанные файлы, сообщения на устройствах и резервные копии. Не загружайте маркетинговую аудиторию без отдельного добровольного согласия.

## Доставка ежедневных отчётов

После обычного перезапуска уже отправленные части не дублируются. При известном отказе Telegram сохраняется возможность безопасного повтора неотправленной части. При разрыве соединения невозможно достоверно отличить «не доставлено» от «доставлено без полученного ответа»: запись становится `uncertain` и требует `/sales_delivery` и явной сверки `/sales_resolve`. Это осознанный предел Bot API, а не обещание недостижимой exactly-once доставки.

Автоматический отчёт за вчера отправляется после выбранного времени в Алматы. При простое более суток для ранее не созданных отчётов используйте ручной период; уже созданные незавершённые доставки сохраняются и возобновляются. Статус `uncertain` автоматически не пересылается.
